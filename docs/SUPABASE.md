# Подключение Supabase

Supabase используется как основная PostgreSQL-база и провайдер входа. Локальная PostgreSQL из Docker Compose остаётся резервной базой. Без `SUPABASE_DB_URL` приложение продолжает работать в локальном режиме, как и раньше.

## Что куда подключается

- **Данные приложения:** backend подключается к Supabase PostgreSQL через `SUPABASE_DB_URL`. Запросы к рабочим таблицам выполняет только backend.
- **Локальный резерв:** backend держит локальную PostgreSQL из `DATABASE_URL`, зеркалирует в неё облачную базу и при потере связи переключает последующие запросы на локальную.
- **Вход:** браузер входит через Supabase Auth, затем backend проверяет access token и назначенные сервером `app_metadata` и выдаёт собственный подписанный токен приложения. Роль и активность дополнительно сверяются с базой приложения.
- **Чат:** авторизованный Supabase Realtime передаёт новые и изменённые сообщения с RLS-фильтрацией каналов. Серверный WebSocket остаётся резервом и обслуживает остальные живые события, а также чат при локальном режиме.

## Настройка проекта Supabase

1. Создайте проект на [supabase.com](https://supabase.com) и сохраните пароль PostgreSQL.
2. В **Project Settings → API** скопируйте Project URL, anon/publishable key и service_role/secret key.
3. В **Project Settings → Database → Connection string** выберите **Session pooler** и скопируйте URI подключения. Для SQLAlchemy в строке должен использоваться драйвер `postgresql://`; приложение само добавит psycopg и `sslmode=require`. Если пароль содержит специальные символы URI, закодируйте их.
4. Заполните `.env` в корне проекта:

```dotenv
SUPABASE_URL=https://YOUR-PROJECT-REF.supabase.co
SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_ONLY_SERVICE_ROLE_OR_SECRET_KEY
SUPABASE_DB_URL=postgresql://postgres.PROJECT-REF:URL-ENCODED-PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres
DB_CHECK_S=5
DB_MIRROR_MIN=5
```

`SUPABASE_SERVICE_ROLE_KEY` нужен backend для автоматического создания/обновления аккаунтов сотрудников в Supabase Auth. Его нельзя помещать во frontend-переменные, отдавать браузеру или коммитить. Публичный anon/publishable key секретом не является, но он не получает прав на таблицы приложения, кроме защищённого RLS чтения чата через Realtime.

5. В новом проекте Supabase откройте Dashboard → **SQL Editor**, вставьте целиком [`supabase_setup.sql`](supabase_setup.sql) и выполните один раз. Скрипт создаёт все 21 таблицу, 6 представлений, индексы, ограничения, RLS и публикацию Realtime. Он предназначен для пустой базы и не является миграцией существующей базы.
6. Запустите приложение обычным способом через Docker Compose. Локальная база Compose остаётся включённой: именно она нужна для failover. Backend подключится к созданной схеме, добавит справочные данные и при пустой облачной базе перенесёт туда существующие локальные данные. В демо-режиме backend также создаёт Auth-пользователей. Убедитесь, что `/api/v1/health` показывает `"database": "supabase"` и `"supabase_connected": true`.
7. Если обе базы уже содержат рабочие данные после незавершённого аварийного режима, приложение остановит автоматический перенос, сохранит локальные изменения и запросит решение администратора, а не будет молча перезаписывать облако. После запуска проверьте экран **Данные → База данных**.

## Supabase Auth и пользователи

Когда задан service key и включён демо-режим, backend создаёт тестовых пользователей Supabase Auth при запуске. Их логины имеют вид `admin@allur.local`, `director@allur.local`, `smena1@allur.local` и т. д. При первом успешном входе локального сотрудника его Auth-аккаунт также создаётся/обновляется автоматически, в том числе при входе по PIN. Для PIN из 4–5 цифр приложение использует совместимый с политикой Supabase Auth пароль `Allur-<PIN>`; пользователю по-прежнему достаточно ввести свой обычный PIN в форму приложения.

Кнопка **Синхронизировать демо-пользователей в Supabase** в разделе базы данных позволяет запустить синхронизацию вручную. Ошибки операции отображаются в интерфейсе. Service key для обычной проверки access token не используется: backend подтверждает токен через endpoint `/auth/v1/user` с anon/publishable key.

Для входа через Supabase пользователь должен соответствовать активному сотруднику приложения с тем же логином. Backend сравнивает с профилем сотрудника также `user_id`, роль и участок из серверных `app_metadata`; изменяемые пользователем `user_metadata` не назначают разрешения. Заявки на регистрацию в приложении остаются локальными и требуют одобрения администратора.

Supabase Realtime для чата требует, чтобы браузерная Supabase Auth-сессия была активна. Она сохраняется в хранилище сессии браузера и удаляется при выходе или отзыве токена приложения. При недоступности Auth или Realtime чат продолжает получать события через backend WebSocket.

Если Supabase Auth недоступен, форма входа пытается использовать локальный вход. После успешного входа через Supabase backend выдаёт токен приложения, который остаётся валиден при временной потере связи с Supabase до истечения `TOKEN_TTL_HOURS`.

## Резервная база и восстановление

- Backend проверяет соединение с Supabase каждые `DB_CHECK_S` секунд. Два последовательных неудачных ping или обнаруженный обрыв соединения переводят новые операции на локальную базу. Запрос, во время которого оборвалась связь, может завершиться ошибкой; повторите эту операцию после появления уведомления о резервном режиме.
- Пока работает основная база, локальная копия обновляется полным снимком раз в `DB_MIRROR_MIN` минут. Это резервная копия с таким интервалом, а не синхронная реплика: последние изменения после недавнего зеркалирования могут отсутствовать в ней.
- После перехода на локальную базу из-за сбоя приложение автоматически переносит локальные изменения обратно, когда Supabase снова доступен. Перенос заменяет облачные таблицы снимком локальной базы, поэтому не вносите параллельные изменения напрямую в Supabase во время аварийного режима.
- Если приложение **запустилось** без соединения с Supabase, оно работает на локальной базе и показывает состояние ожидания решения. После восстановления связи администратор выбирает на экране базы данных: перенести локальный снимок в Supabase или вернуться без переноса. Это защищает облачные данные от случайной перезаписи устаревшей локальной копией.
- Не удаляйте volume `allur-db`: в нём находится локальный резерв.

## Переменные окружения

| Переменная | Значение по умолчанию | Назначение |
|---|---:|---|
| `SUPABASE_URL` | пусто | URL проекта, нужен для Auth и синхронизации демо-аккаунтов. |
| `SUPABASE_ANON_KEY` | пусто | Публичный ключ Auth. Никаких прав на таблицы приложения ему не выдаётся. |
| `SUPABASE_SERVICE_ROLE_KEY` | пусто | Только backend: создание/обновление пользователей Supabase Auth. |
| `SUPABASE_DB_URL` | пусто | PostgreSQL Supabase. Пустое значение оставляет приложение на локальной базе. |
| `DB_CHECK_S` | `5` | Интервал проверки основной базы, секунды. |
| `DB_MIRROR_MIN` | `5` | Интервал полного снимка Supabase в локальную базу, минуты. |
